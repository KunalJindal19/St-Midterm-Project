\section*{Overview}
\addcontentsline{toc}{section}{Overview}

This report describes an agentic pipeline for AI-assisted unit testing. For each problem of the MBPP dataset, the pipeline generates a Python function with a Large Language Model (LLM), generates unit test cases that are intended to satisfy a structural coverage criterion selected by the user, executes those test cases against the generated function, and reports a verdict. In addition, the pipeline verifies automatically whether the executed test cases actually satisfy the selected criterion.

\begin{insight}{Test requirement implemented}
The assignment admits three kinds of test requirement. This project implements \textbf{requirement (1): a user-specified coverage criterion}. The user selects one of four graph coverage criteria defined on the control flow graph (CFG) of the generated function: \textbf{Node}, \textbf{Edge}, \textbf{Edge-Pair} or \textbf{Prime Path} coverage, the last being the default.
\end{insight}

\begin{insight}[primary]{Design from first principles}
The pipeline is implemented in plain Python. It does not use retrieval-augmented generation, chain-of-thought prompting or agent frameworks such as LangGraph. Each LLM agent issues a single request consisting of one system message and one user message, and the prompts explicitly forbid the model from presenting its reasoning. The agents are sequenced by ordinary Python control flow.
\end{insight}

The report is organised according to the five items required by the assignment: the pipeline and the dataset (Section~\ref{sec:pipeline}), the prompts and settings (Section~\ref{sec:prompts}), the formats of the generated code, test cases and verdicts together with actual examples (Section~\ref{sec:formats}), the execution results (Section~\ref{sec:results}), and the contribution of each member (Section~\ref{sec:contrib}).

\subsection{Dataset}

The pipeline uses the \textbf{MBPP (Most Basic Python Problems)} dataset, configuration \texttt{full}, \texttt{test} split (\texttt{google-research-datasets/mbpp}), loaded with the Hugging Face \texttt{datasets} library. Each problem provides:
\begin{itemize}[nosep]
    \item a natural-language description of the task;
    \item a reference solution in Python;
    \item three reference \texttt{assert} statements, from which the name of the function under test is obtained and which are shown to both LLM agents as example usage.
\end{itemize}
The user specifies the number of problems to process (1--50, default 1). Problems are processed in dataset order, beginning with task 11.

\subsection{Processing of One Problem}

\newcommand{\stepnum}[1]{\tikz[baseline=(n.base)]\node[circle, fill=primary, text=white, inner sep=1.6pt, minimum size=1.3em, font=\scriptsize\sffamily\bfseries] (n) {#1};}
\begin{enumerate}[label=\protect\stepnum{\arabic*}, leftmargin=2.2em]
    \item The name and signature of the function under test (for example \texttt{remove\_Occ(s, ch)}) are derived from the reference solution; the name is that of the function invoked in the MBPP assertions.
    \item The \textbf{Code Generator} requests the function from the LLM. The response is accepted only if it consists of exactly one top-level function definition with the required name. Otherwise the LLM is prompted once more, with the reason for the rejection appended to the prompt.
    \item The \textbf{Test Case Generator} requests test cases that satisfy the selected coverage criterion on the generated code. The reference solution is not disclosed to this agent. The response is accepted only if it consists exclusively of test cases in the prescribed format; otherwise the LLM is prompted once more with the reason for the rejection.
    \item The \textbf{Test Executor} parses each test case and executes the reference solution on its input. A test case is valid only if the reference output equals the expected output. The generated function is then executed on every valid test case in a separate process with a time limit of 10\,s per call, and the assertion \texttt{generated(*args) == expected} is evaluated. Finally, the executor constructs the CFG of the generated function, records the path that each test case follows through it, and determines whether the selected criterion is satisfied.
    \item All prompts, raw LLM responses, generated code, test cases and results are written to the directory \texttt{output/}.
\end{enumerate}

\subsection{Automatic Verification of the Coverage Criterion}
\label{sec:verification}

The LLM is instructed to reason about the CFG of the generated function, but there is no guarantee that it does so correctly. The Test Executor therefore verifies the criterion independently (\texttt{coverage\_probe.py}):
\begin{enumerate}
    \item \textbf{Control flow graph.} The generated function is parsed with the \texttt{ast} module and its CFG is constructed. Consecutive statements are grouped into basic blocks, which form the nodes of the graph, and a synthetic \emph{exit} node is added as the final node. Each \texttt{if}/\texttt{elif}/\texttt{while} condition forms a single decision node (a compound condition such as \texttt{a or b} is not decomposed), and every loop header is a node of its own. The constructs \texttt{break}, \texttt{continue}, \texttt{return}, loop \texttt{else} clauses and \texttt{try}/\texttt{except} are modelled; nested helper functions are treated as single statements.
    \item \textbf{Test paths.} In the same pass, a copy of the function is instrumented with probe calls. The input of every valid test case is executed on this copy, which records the sequence of CFG nodes visited, i.e.\ the test path. Each recursive call yields a separate test path.
    \item \textbf{Test requirements.} For all four criteria the test requirements are derived from the CFG following Ammann and Offutt. Prime paths are obtained by enumerating all simple paths and retaining the maximal ones; the implementation reproduces the eight prime paths of the textbook example.
    \item \textbf{Touring.} A test requirement is covered if it occurs as a contiguous sub-path of at least one test path. The selected criterion is reported as \emph{met} if and only if all of its test requirements are covered.
\end{enumerate}
The verdict is always computed on the original, uninstrumented function; the instrumented copy serves only to record test paths. Whether a path is executable cannot be decided automatically in general, so an uncovered requirement may be \emph{infeasible}. Uncovered requirements are therefore listed explicitly for inspection.

\section{Prompts and Settings}
\label{sec:prompts}

Both LLM agents use a temperature of 0.7 and a limit of 4,096 output tokens. Each request contains one system message and one user message, without conversation history. For every problem, the prompts, the model that produced each response and the raw responses are stored in \texttt{code\_gen\_prompts.json} and \texttt{test\_gen\_prompts.json}.

When a model is rate-limited (HTTP 429), the client waits for the \texttt{Retry-After} interval and repeats the request once. When a model is unavailable (HTTP 404, 502 or 503), or when its response was truncated at the token limit (\texttt{finish\_reason = "length"}), the next fallback model is used. Only the final \texttt{content} of a response is used; reasoning fields returned by some models are ignored.

\subsection{Code Generator Prompts}

\begin{prompt}{Code Generator -- system prompt}
You are a Python code generator in an automated unit-testing pipeline. Your response is loaded by a program that calls your function with test inputs, so it must be exactly one Python 3 function definition and nothing else.

Rules:
1. Write exactly one function, with exactly the name and parameters given in the user message.
2. Put any import statements and helper functions INSIDE the function body. Nothing may appear before or after the function.
3. The function must return its result. Do not print, do not read input(), and do not include example usage, test cases or assert statements.
4. Do not write any text outside the function: no reasoning or thinking process, no explanations and no markdown code fences (```).
5. The first line of your response must be `def <function name>(`.
\end{prompt}

The user prompt is constructed from the problem description, the required signature and the three MBPP assertions.

\begin{prompt}{Code Generator -- user prompt (task 11)}
Problem description:
Write a python function to remove first and last occurrence of a given character from the string.

Required function signature:

A prime path is a simple path (no node appears twice, except that the first and last node may be the same) that is not a proper sub-path of any other simple path. EXPECTED OUTPUTS

\section{Format of the Code, Test Cases and Verdicts}
\label{sec:formats}

The generated code is a single Python function; each test case is a pair of tagged blocks containing Python literals; and the verdicts are stored as one JSON record per problem. All examples in this section are actual outputs of the final pipeline run for task 11 (\texttt{output/task\_11}).

\subsection{Generated Code}
\label{sec:codeformat}

The generated code consists of exactly one function with the required name and parameters; imports and helper functions, if any, are placed inside the function body.

\begin{pycode}{generated\_code.py -- raw LLM response, accepted at the first attempt}
def remove_Occ(s, ch):
    first = s.find(ch)
    if first == -1:
        return s
    last = s.rfind(ch)
    if first == last:
        return s[:first] + s[first+1:]
    else:
        return s[:first] + s[first+1:last] + s[last+1:]
\end{pycode}

\begin{pycode}{reference\_code.py -- MBPP reference solution, used only to validate test cases}
def remove_Occ(s,ch):
    for i in range(len(s)):
        if (s[i] == ch):
            s = s[0 : i] + s[i + 1:]
            break
    for i in range(len(s) - 1,-1,-1):
        if (s[i] == ch):
            s = s[0 : i] + s[i + 1:]
            break
    return s
\end{pycode}

Each test case consists of two blocks. The first contains the arguments of one call as Python literals separated by \texttt{\$}; the second contains the expected return value.

\begin{prompt}{test\_cases.txt -- task 11, Prime Path Coverage (raw LLM response)}
<OPEN>"hello"$"x"<CLOSE><OPEN>"hello"<CLOSE><OPEN>"hello"$"e"<CLOSE><OPEN>"hllo"<CLOSE><OPEN>"hello"$"l"<CLOSE><OPEN>"heo"<CLOSE>
\end{prompt}

The executor parses this string as follows:
\begin{itemize}
    \item The string is split at the \texttt{<OPEN>}/\texttt{<CLOSE>} tags, and consecutive blocks are paired as (arguments, expected output).
    \item The arguments are split at every \texttt{\$} that lies outside string literals and brackets, so that values such as \texttt{"a\$b"} and \texttt{\{"k": [1, 2]\}} are parsed correctly.
    \item Each value is converted with \texttt{ast.literal\_eval}; a small set of safe constructors such as \texttt{set()} and \texttt{float("inf")} is also accepted. No code produced by the test generator is ever executed.
    \item A test case that cannot be parsed, for instance because of an unquoted string or a missing tag, is marked \INVALID{} individually; the remaining test cases are processed normally.
\end{itemize}

For each valid test case the executor evaluates the equivalent of the following assertions:

\begin{pycode}{Assertions evaluated for task 11}
assert remove_Occ("hello", "x") == "hello"
assert remove_Occ("hello", "e") == "hllo"
assert remove_Occ("hello", "l") == "heo"
\end{pycode}

Floating-point values are compared with a relative and absolute tolerance of $10^{-9}$; all other values are compared with the Python operator \texttt{==}.

The verdict of a problem is determined from its valid test cases:
\begin{itemize}[nosep]
    \item \PASS{} if all valid test cases pass;
    \item otherwise \FAIL, \ERROR{} or \TLE, in this order of precedence;
    \item \INVALID{} if the suite contains no valid test case;
    \item \NOTRUN{} if code generation or test generation failed.
\end{itemize}
Independently of the verdict, the coverage report states whether the selected criterion is \emph{met}.

The collaboration followed these principles:
\begin{itemize}
    \item \textbf{Interfaces first.} Before implementation, three contracts were fixed: the format of the generated code (a single function), the \texttt{<OPEN>}/\texttt{<CLOSE>} test-case format and the schema of \texttt{execution\_results.json}. This allowed both members to develop their modules concurrently.
    \item \textbf{One owner, one reviewer.} Each module had a single owner and was reviewed by the other member before integration. The author of each agent reviewed the other agent, so that both members were familiar with the entire pipeline.
    \item \textbf{Daily synchronisation.} Progress, obstacles and the distribution of work were discussed at the beginning and end of each day.
    \item \textbf{Shared request budget.} Because the free OpenRouter models impose per-minute and per-day limits, end-to-end runs were scheduled rather than executed by both members simultaneously.
    \item \textbf{Joint debugging during integration.} Format deviations of the free models, such as markdown fences, unquoted strings and responses containing reasoning text, were analysed and resolved jointly.
    \item \textbf{Divided writing, mutual proofreading.} Each member wrote two sections of the report and proofread the other two; the contributions and conclusions were written jointly.
\end{itemize}

\section*{Observations and Conclusion}
\addcontentsline{toc}{section}{Observations and Conclusion}

Coverage-driven test generation achieved full structural coverage on the MBPP problems with a small number of test cases. The experiments also show, however, that the criterion must be verified independently of the LLM, and that full coverage of the generated code does not by itself demonstrate the absence of faults.

\begin{tcbraster}[raster columns=2, raster equal height=rows, raster column skip=4mm, raster row skip=4mm, raster every box/.style={halign=flush left}]
    \begin{insight}[primary]{Oracle problem}
        The LLM predicts the expected outputs itself. Each prediction is checked against the MBPP reference solution, and the generated code is executed only on confirmed test cases. The generator never sees the reference solution and is informed that the code under test may be faulty.
    \end{insight}
    \begin{insight}[accent]{Automatic coverage verification}
        The LLM's reasoning about the CFG cannot be relied upon. The executor therefore constructs the CFG itself, records the test paths and checks every test requirement. Requirements that are infeasible cannot be recognised automatically in general and are reported as uncovered for inspection.
    \end{insight}
    \begin{insight}[fail]{Coverage does not reveal faults of omission}
        The three test cases of task 11 achieve full prime path coverage, yet a deliberately wrong implementation, \texttt{return s.replace(ch, '')}, which removes every occurrence, passes all of them, because no test case contains the character three or more times. Coverage of the generated code exercises only paths that exist in that code.
    \end{insight}
    \begin{insight}[pass]{Detection of incorrect code}
        A faulty implementation of \texttt{remove\_Occ} returning \texttt{s[:first] + s[last+1:]} was reported as \FAIL{} on the input \texttt{("abcda", "a")}.
    \end{insight}
    \begin{insight}[llm]{Output formats and reasoning models}
        In one earlier run a fallback reasoning model wrote its entire reasoning (13,660 characters) into the response and was truncated before producing an answer. Responses are now accepted only if they consist exclusively of test cases, truncated responses are discarded, and malformed individual test cases (such as \texttt{[[]<, []]} in task 12) are isolated.
    \end{insight}
    \begin{insight}[invalid]{Robustness and rate limits}
        Each call runs in its own process with a limit of 10\,s, so an infinite loop or exception affects only one test case. Free models limit requests per minute and per day; the client therefore retries once and falls back through five further models, as occurred for task 12.
    \end{insight}
\end{tcbraster}

\begin{insight}[primary]{Conclusion}
The project implements, from first principles, a three-agent pipeline consisting of an LLM code generator, an LLM test case generator driven by a user-selected structural coverage criterion, and a deterministic test executor. The executor validates each test case against the MBPP reference solution, asserts the output of the generated function, and verifies node, edge, edge-pair and prime path coverage on the control flow graph of the generated function. The results demonstrate that coverage-driven generation combined with independent verification yields reliable verdicts, while also showing that structural coverage alone cannot detect missing behaviour.
\end{insight}
